# OpenAI Realtimeセッションの自動再接続: 要件

Issue: [#2](https://github.com/satoryu/koemieru/issues/2) · 設計: [design.md](design.md) · タスク: [tasks.md](tasks.md)

## Problem Statement

実際のZoomオンライン講演でKoemieruをリアルタイム文字起こしに使ったところ、**開始から60分経過した時点でOpenAI Realtime APIの1接続あたりのセッション時間上限に達し、文字起こしが停止した**。ユーザーが停止に気づいて手動で再開するまで、その間の発話はすべて失われる。

OpenAIのRealtimeセッションはWebSocket / WebRTCのいずれでも**最長60分**で、公式に延長する手段はなく、接続を張り直す以外にない。講演・会議・授業は60分を超えるのが普通であり、Koemieruが想定する主用途（長時間の音声を聞きながら文字で追う）において、この上限は実運用上の致命的な制約になっている。

同じ問題は60分上限に限らない。ネットワークの瞬断、OpenAI側の一時的なエラー、スリープ復帰なども同じく接続断として現れ、現状はいずれもセッション全体の停止につながる。

なお、この項目は[docs/1-koemieru-mvp/design.md](../1-koemieru-mvp/design.md)に「既知の限界事項：切断時の自動再接続なし」として意図的に見送っていたものであり、実運用で顕在化したため本Issueで解消する。

## Requirements

### 機能要件

- **FR-1**: OpenAIとのWebSocketが予期せず切断された場合、ユーザーの操作なしに自動で再接続し、文字起こしを継続する。
- **FR-2**: 再接続の対象は60分上限に限らず、**予期しない切断すべて**とする（ネットワーク瞬断、サーバ側の一時的エラーを含む）。
- **FR-3**: 再試行しても回復しないエラー（APIキーが無効、クレジット残高切れ）については再接続を試みず、ただちにセッションを終了し、エラー内容をサイドパネルに表示する。
- **FR-4**: 再接続は指数バックオフで行い、試行回数に上限を設ける。上限に達したらセッションを終了し、ユーザーに再開を促す。
- **FR-5**: 切断中に到着した音声チャンクを上限付きで保持し、再接続完了後に順序どおり送り直す。これにより切断中の発話も文字起こしされる。
- **FR-6**: 再接続中であることをサイドパネルのステータス欄に表示する（何回目の試行かを含む）。再接続に成功したら通常のステータス表示に戻る。
- **FR-7**: 再接続中でもStopボタンは有効で、押せばただちに停止する（保留中の再接続も取り消される）。
- **FR-8**: 再接続の前後で文字起こしの内容が失われたり、重複したりしない。

### 非機能要件

- **NFR-1**: 再接続中もタブの音声再生は途切れない。音声パイプライン（MediaStream / AudioContext / AudioWorklet）はWebSocketの切断に巻き込まれてはならない。
- **NFR-2**: 再接続ロジックは実際のネットワーク接続なしにユニットテストできること（フェイクWebSocketと擬似タイマーで検証可能な設計にする）。
- **NFR-3**: 再接続によってオフスクリーンドキュメントが閉じられたり、タブキャプチャの権限を取り直す必要が生じたりしないこと（`chrome.tabCapture`はユーザージェスチャーを要求するため、権限の取り直しが必要になると自動再接続は成立しない）。
- **NFR-4**: APIキーはこれまでどおりログにも画面にも出力しない。

## Constraints

- **C-1**: OpenAI Realtimeセッションの60分上限は仕様であり、延長する手段はない。張り直すしかない。
- **C-2**: OpenAIは60分上限到達時に返すエラーコードを公式ドキュメントに記載していない。したがって「期限切れを表すコード」を判定して再接続する設計にはできず、逆に「再試行しても無意味なエラー」を列挙する方式を取る必要がある。
- **C-3**: 切断した時点でサーバ側の入力音声バッファは失われる。直前の未コミット分を救えるのはクライアント側に保持したデータだけである。
- **C-4**: 再接続すると新しいセッションになり、文字起こしイベントの`item_id`が振り直される。セッションをまたいで同じIDが再利用される可能性を排除できない。
- **C-5**: `chrome.tabCapture`はユーザージェスチャーからしか開始できない（[MVPの設計](../1-koemieru-mvp/design.md)参照）。よって再接続の実装は、既存のMediaStreamを保持したままWebSocketだけを張り直す形でなければならない。

## Acceptance Criteria

1. 文字起こし中にネットワークを一時的に切断すると、サイドパネルのステータスが再接続中を示す表示に変わり、回線復帰後に自動的に文字起こしが再開される。ユーザーの操作は不要。
2. 上記1の間、キャプチャ中のタブの音声は途切れず鳴り続ける。
3. 切断中に発話された内容が、再接続後の文字起こしに現れる（上限内の長さであれば欠落しない）。
4. 無効なAPIキーで開始した場合、再接続ループに入らず、ただちにエラー内容がサイドパネルに表示される。
5. 再接続待ちの最中にStopを押すと、ただちに`Idle`に戻り、保留中の再接続は実行されない。オフスクリーンドキュメントも残らない。
6. 60分を超える連続稼働で、上限到達時に自動で接続が張り直され、文字起こしが継続する。
7. 再接続の前後で文字起こしテキストに重複や欠落がない。
8. `pnpm test` / `pnpm compile` / `pnpm build` がすべてグリーンである。

## User Stories

- **US-1**: 90分の講演を聞いている参加者として、60分を過ぎても文字起こしが勝手に止まらないでほしい。止まったことに気づけず、後から議事録を見返して初めて欠落に気づくのが一番困る。
- **US-2**: 会議中の参加者として、Wi-Fiが一瞬切れたくらいで文字起こしをやり直したくない。復帰したら勝手に続きを拾っていてほしい。
- **US-3**: ユーザーとして、再接続を試みている最中なのか、それとも本当に止まってしまったのかを画面で区別できてほしい。止まっているなら自分で再開する必要があるからである。
- **US-4**: ユーザーとして、APIキーが間違っている・クレジットが切れているといった自分で直すしかない問題のときは、無駄に再試行を繰り返さず、すぐ理由を教えてほしい。

## Target Validation Scenario

60分を超える音源（実際のオンライン講演、または長時間の動画）でキャプチャを開始し、そのまま最後まで放置する。60分の境界で自動的に接続が張り直され、文字起こしが最後まで途切れずに続くこと、および前後で内容の重複・欠落がないことを確認する。結果はIssue #2に記録する。
